# 04 — Cursor Execution Domain

Entities: **Cursor Session**, **Cursor Revision**

---

## 1. Cursor Session

### Purpose

Record of a single Cursor IDE execution against an approved Prompt Version — the bridge between AOS planning and code changes.

### Ownership

| Aspect | Owner |
|--------|-------|
| Data | AOS |
| Executor | ERP user (referenced) |

### Lifecycle

```
started → captured → evaluated → passed | failed | revised
```

| State | Meaning |
|-------|---------|
| `started` | Developer began execution (honor system or manual trigger) |
| `captured` | Developer submitted capture template |
| `evaluated` | Evaluation Engine scored output |
| `passed` | Evaluation met threshold |
| `failed` | Evaluation below threshold |
| `revised` | Revision prompt created; links to Cursor Revision |

Terminal states: `passed`, `failed` (if no revision pursued)

### Relationships

| Related entity | Cardinality | Required? |
|----------------|-------------|-----------|
| Prompt Version | many-to-one | **Required** |
| Prompt Artifact | many-to-one | Denormalized |
| Prompt Pack | many-to-one | Denormalized |
| Delivery Engagement | many-to-one | Denormalized |
| Executor (ERP user) | many-to-one | **Required** |
| Evaluation | one-to-one | **Required** after capture |
| Cursor Revision | one-to-one | Optional (if failed → revise) |
| Requirement(s) | many-to-many | Optional traceability |

### Invariants

1. Must reference exactly one Prompt Version
2. Prompt Version must be in `published` state
3. Parent Prompt Artifact must be `approved` at session start
4. One primary evaluation per session (re-evaluations create new evaluation records)
5. Capture must include change summary before evaluation triggers
6. Same `companyId` throughout chain

### Business Rules

| Rule | Description |
|------|-------------|
| BR-CS-01 | 100% of delivery code changes should trace to a session (policy) |
| BR-CS-02 | Session capture includes: files changed list, change summary, self-assessment |
| BR-CS-03 | Failed session blocks next artifact in pack until revision passes |
| BR-CS-04 | Multiple sessions per Prompt Version allowed (re-execution after revision) |
| BR-CS-05 | Integration Level 1 (manual handoff) in Phase 3; automation deferred |

### Creation Rules

- Created when developer starts execution against approved Prompt Version
- Executor must be engagement team member or have `aos_cursor_execute`

### Update Rules

- Capture fields editable until `evaluated`
- State transitions system-driven after evaluation
- Immutable after `passed`

### Deletion Rules

- **Append-only — never delete**
- Failed sessions preserved for learning

### Versioning Strategy

- Sessions are point-in-time records, not versioned
- Re-execution creates new session against same or new Prompt Version

### Audit Requirements

`aos_cursor_session_started`, `aos_cursor_session_captured`, `aos_cursor_session_passed`, `aos_cursor_session_failed`

### Future Extensibility

- Automated capture via Cursor SDK (Level 3)
- Agent transcript storage (file storage TBD)
- Git diff integration
- Duration and token usage metrics

### Cross-Layer Interaction

- None with ERP/BOS data stores
- ActivityLogger records session events

## 2. Cursor Revision

### Purpose

Links a failed Cursor Session to the revised Prompt Version created to address evaluation failures — maintains revision chain integrity.

### Ownership

| Aspect | Owner |
|--------|-------|
| Data | AOS |
| Parent | Cursor Session (failed) |

### Lifecycle

```
created → revision_executed → resolved
```

| State | Meaning |
|-------|---------|
| `created` | Revision Prompt Version generated |
| `revision_executed` | New session run against revision version |
| `resolved` | Revision session passed |

### Relationships

| Related entity | Cardinality | Required? |
|----------------|-------------|-----------|
| Original Cursor Session | one-to-one | **Required** (failed session) |
| Original Evaluation | one-to-one | **Required** (failure evidence) |
| Revision Prompt Version | many-to-one | **Required** |
| Revision Cursor Session | one-to-one | Optional until executed |
| Prompt Artifact | many-to-one | Denormalized |

### Invariants

1. Can only exist for sessions in `failed` state
2. Revision Prompt Version must be child of same Prompt Artifact as original
3. Revision version number > original version number
4. Must include failure analysis summary (from Evaluation)
5. One active revision chain per failed session

### Business Rules

| Rule | Description |
|------|-------------|
| BR-CR-01 | Revision prompt generated by AI Orchestration from evaluation evidence |
| BR-CR-02 | Human must approve revision Prompt Version before re-execution |
| BR-CR-03 | Maximum revision cycles configurable (default: 5 per artifact) |
| BR-CR-04 | Exceeded revision limit escalates to delivery lead review |

### Creation Rules

- System-created on evaluation failure (or manual trigger)
- Links automatically to source session and evaluation

### Update Rules

- State transitions only
- Immutable after `resolved`

### Deletion Rules

- **Forbidden** — learning data

### Versioning Strategy

- Revision references Prompt Versions; does not version itself

### Audit Requirements

`aos_cursor_revision_created`, `aos_cursor_revision_resolved`, `aos_cursor_revision_limit_reached`

### Future Extensibility

- Auto-generate revision prompts without human draft step
- Revision pattern analysis for Knowledge Engine

### Cross-Layer Interaction

- None

## Cursor Domain — Relationship Summary

```
Prompt Version (1) ──→ (0..n) Cursor Session
Cursor Session (1) ──→ (1) Evaluation
Cursor Session (1) ──→ (0..1) Cursor Revision [if failed]
Cursor Revision (1) ──→ (1) Prompt Version [revision]
Cursor Revision (1) ──→ (0..1) Cursor Session [re-execution]
```

**Company isolation:** Denormalized `companyId` on all records.

**ERP/BOS:** No direct interaction.
